# TrSS Game Library & Recorder — Developer README

**My working notes for the recorder, current as of 15 October 2026.** This document records what I have built, what it actually measures, where the implementation lives, and what remains before I can rely on it for serious performance or neural-rendering research.

## What I am building

TrSS has two first-party Windows recording interfaces:

- **TrSS Game Library** (`trss-recorder`) is the main app. It discovers installed games, presents game cards, launches a selected executable or supported store URI, shows available monitoring counters, records opt-in samples, and asks me to review the game's graphics settings after each capture.
- **TrSS Data Recorder** (`trss-window-recorder`) is the older, simpler single-window capture utility. It is useful when I need to select a visible application window without using the game library.

The recorder is deliberately independent of the live TrSS graphics runtime. It can make a Baseline recording without TrSS installed and a second recording with TrSS enabled. It does not have to inject into, connect to, or load the renderer.

## Current implementation status

| Capability | Current state |
| --- | --- |
| Game discovery | Implemented: Steam manifests, Epic manifests, common install locations, game-like uninstall entries, manually selected folders, and optional deeper drive scan |
| Game cards and launch | Implemented; title/store-specific launch behavior can still vary |
| Executable icons | Extracted for local UI; local icon cache |
| Local performance overlay | Implemented for counters Windows exposes, including CPU, memory and some per-process GPU/VRAM counters |
| Opt-in screen sampling | Implemented for visible, focused application windows; configured game-library rates are 1, 2, 5, or 10 screenshots per second |
| Session metadata and ZIP bundle | Implemented; the Game Library writes timestamped `performance.jsonl` into each bundle, then checks the ZIP CRC and verifies the embedded SHA-256 manifest against every archived file before cleanup |
| Graphics settings review | Implemented after a capture; recognized config keys can be suggested, then values must be checked against the game's own settings menu for an exact row |
| Shared graphics matrix | Implemented as local `game-matrix.csv` and `game-matrix.jsonl` files under the Windows local application-data folder |
| Baseline versus TrSS comparison | Implemented for rows that match game, experiment group, and settings fingerprint; CSV and JSON outputs |
| Native game FPS / frametime / 1% lows | **Not implemented.** Values stay unavailable instead of being inferred |
| Renderer-native color/depth/motion/history capture | **Not implemented.** Current samples are screenshots, not engine buffers |
| Paired low-resolution inputs and high-quality reference renders | **Not generated by the recorder**; must come from a properly controlled, legally usable capture pipeline |
| Universal automatic settings detection | Not possible with the current generic config readers; game-specific adapters and manual verification remain necessary |
| Wide real-world compatibility validation | Still required across Windows versions, drivers, game APIs, display modes, store launchers, and long captures |

Do not describe screenshot sample rate as game FPS. Do not claim that this recorder alone creates a supervised neural-rendering dataset.

## Install and run locally

Requirements: Windows 10/11, Python 3.10 or newer, Tkinter, and a writable local application-data folder. From the repository root, use PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[test]"
```

Launch the main game library. Use **Capture folder** in the library footer to select another drive; the destination is saved locally:

```powershell
trss-recorder
```

Launch the standalone recorder:

```powershell
trss-window-recorder
```

Run checks:

```powershell
python -m pytest -q
```

The Windows workflow packages the game library into a single-file x64 executable named `TrSS-Game-Library.exe` and produces a companion SHA-256 file. Download the `TrSS-Game-Library-windows-x64` artifact from a completed workflow run. A successful packaging job proves only that CI built the app and its tests passed; it is not a substitute for launching the executable on my Windows PC.

## How I use a game-library recording

1. Launch TrSS Game Library and select a detected title. If discovery misses it, use **Add folder** or the optional deeper drive scan.
2. Launch the title from its game card when supported. Some store, launcher, Microsoft Store, or protected titles may require their own launch path or might not work through a discovered executable.
3. Confirm both consent options before capture. Make sure the screen content is mine to record and share.
4. Focus the game's window, then press **Ctrl + Alt + F8** to start or stop a capture. The selected sampling rate is 1, 2, 5, or 10 screenshots each second; available performance counters are sampled at roughly one-second intervals.
5. Press **Ctrl + Alt + F10** to stop early, or **Ctrl + Alt + F9** to restore the library. Sampling stops when the chosen window loses focus, capture errors occur, or the app must preserve disk space to finish the archive safely.
6. Complete the **Graphics Profile / Post-Capture Review**. Check suggested settings against the game's actual Graphics/Display menu. Only mark a profile verified when I have actually checked the menu. Give related runs the same experiment-group label.
7. Review the session bundle and screenshots before sharing. Compare only rows that have matching game, experiment group, and graphics-settings fingerprint.

The exact keyboard behavior is documented in [RECORDER.md](RECORDER.md). The two Ctrl+Alt+F8 actions mean start/stop; Ctrl+Alt+F10 is the stop-now route, and Ctrl+Alt+F9 restores the library.

## What is saved

Per-session bundles can contain:

- `metadata.json`: session details, consent flags, coverage and verification state, and limitations.
- `system.json`: available OS, CPU, GPU-driver labels, and installed-memory details.
- `sequence.jsonl`: ordered frame IDs, timestamps, session ID, and relative PNG paths.
- `frames/frame-XXXXXXXX.png`: lossless screenshot samples.
- `performance.jsonl`: available timestamped CPU, memory, and per-process GPU measurements. FPS and frametime stay unavailable until a first-party frame-event collector exists.
- `graphics_settings.json`: normalized values and source/verification metadata from post-capture review.
- `game_matrix_row.json`: one normalized matrix record with completeness, profile, settings hash, and available metric summaries.
- `SHA256SUMS.txt`: integrity checksums for packaged files.
- `README.txt`: human-readable bundle contents and privacy caveats.

The shared matrix is stored at:

```text
%LOCALAPPDATA%\TrSS\GameLibrary\matrix\game-matrix.csv
%LOCALAPPDATA%\TrSS\GameLibrary\matrix\game-matrix.jsonl
```

The CSV is convenient for spreadsheets. JSONL retains the richer row structure. Both remain local unless I deliberately share them.

## Privacy and limits

TrSS is local-first. The recorder does not upload samples, record audio or microphone input, inspect game memory, collect clipboard contents, or bundle a third-party FPS telemetry program. It does not intentionally save the selected raw window title or absolute game installation path to session bundles. Nevertheless, screenshots can contain private messages, account data, or content belonging to other people; inspect captures before sharing them.

The recorder captures visible pixels from a selected window. It does not provide the actual GPU render-target color, depth, motion vectors, reprojection data, or temporal history needed by many neural-rendering models. The game-library sample-rate option is only a screenshot collection rate. It must never be published as real game FPS or used to imply real-time performance.

Config parsing uses a bounded allowlist of recognizable graphics keys. Game config files can be stale, hidden, encrypted, or use numeric values that depend on that game's implementation. Only the game's own menu plus explicit participant confirmation can support an exact settings profile. The matrix is intended to keep uncertainty visible, not remove it.

## Compare Baseline and TrSS runs

Make baseline and TrSS runs using the same game build, scene, resolution, graphics settings, driver, and experiment group. Change the renderer/preset profile only when that is what I intend to compare. Repeat runs when practical, and alternate order if heat/cache effects may affect results.

```powershell
trss-compare-performance --matrix "$env:LOCALAPPDATA\TrSS\GameLibrary\matrix\game-matrix.jsonl" --output-dir "logs\performance-comparison" --baseline-profile "Baseline" --trss-profile "TrSS - Cinematic" --require-exact
```

Use the precise profile name I actually saved. This command pairs only matching games, experiment groups and settings hashes; with `--require-exact`, both profiles must be marked exact and verified in-game. It writes `performance-comparison.csv` and `performance-comparison.json`.

The output currently compares whichever compatible process/system CPU, GPU/VRAM, and RAM metrics exist. Missing FPS and frametime values remain absent. A measured difference is descriptive rather than causal proof: scene variation, background activity, driver behavior, temperatures, caches, and run order can influence results.

These comparison files are **evaluation and optimization evidence**, not direct training targets for image reconstruction. A neural network still needs aligned training/reference frames and actual auxiliary inputs required by its design.

## My next recorder milestones

### 1. Add first-party present/frame-event telemetry

Build a native, documented source for actual application frame events and frametime. Define when a presented frame counts, how dropped/repeated frames are treated, and how measurement overhead is minimized. Validate against known workloads and retain null values whenever a metric cannot be obtained reliably. Then add correct percentile and 1% low calculations from measured frame times, with unit tests.

This milestone must not smuggle in a third-party FPS program or infer FPS from screenshots, refresh rate, or GPU load.

### 2. Improve the app's practical validation

Run the portable executable on the target Windows machine. Verify game scanning, icon loading, launching, capture start/stop, focus-loss behavior, disk-space handling, ZIP creation, checksum verification, graphics review, matrix accumulation, and restore/uninstall behavior. Test long captures on games that are permitted to be used for this research.

### 3. Improve graphics profiles conservatively

Add game-specific settings parsers only when their source format is understood and covered by fixtures/tests. Preserve each setting's detected source and verification state. Never silently convert unknown enum integers into quality labels. Keep a clear path to mark a value unavailable or not applicable.

### 4. Make comparison results statistically more useful

Support repeated-run summaries and clear counts of valid observations while preserving each session's original data. Add guardrails for scene mismatch and profile-label mismatch, document which counters are comparable on different Windows/driver versions, and avoid causal claims without a controlled experiment.

### 5. Treat renderer-buffer capture as a separate project milestone

If I later add native renderer capture, create a clearly separate interface for real color/depth/motion/history sources, with game/API-specific requirements, explicit consent, frame alignment, and buffer validation. Do not pretend screenshot sampling solves this task. Every source needs real data provenance and a documented contract.

## Definition of done for the recorder

I can call the recorder a dependable research-capture tool only after the packaged application has been exercised on the target machine, the available telemetry semantics are validated, the data bundle remains internally consistent, the local matrix survives repeated captures, graphics-setting uncertainty is visible, and failures are safe and recoverable.

I cannot call it a real FPS benchmark until actual frame-event measurements are implemented and validated. I cannot call its screenshot archive a neural-rendering dataset until the required aligned reference frames and actual auxiliary buffers exist.
